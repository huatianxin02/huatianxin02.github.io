我在一台 Mac 上跑通了三套 RAG 系统

一次关于「文档问答」的完整实践 · 2026-10-14

为了搞清楚「让机器读懂工艺文档」这件事到底该怎么做，我用三条完全不同的技术路线各实现了一遍： 从零手写 RAG 全链路、用 Dify 做平台化编排、用 RAGFlow 的 DeepDoc 做深度解析。 最终幻觉率 0%、检索命中率 100%，也摸清了三种方案各自的代价。

引子：一条查不到的工艺参数

假设你是一名汽车电子厂的工艺工程师。产线上波峰焊的锡炉温度偏了，你要查标准值是多少。

你打开那本 200 多页的《SMT 工艺指导书》，Ctrl+F 搜「锡炉」。结果跳出来 17 处， 分布在 6 个不同章节里 —— 有的是设备点检表，有的是参数表，有的是故障处理流程。 你得逐个点开，看上下午的版本号对不对。

于是你想：能不能直接问一句就出答案？

你打开某个大模型，输入「波峰焊锡炉温度标准值是多少」。它很自信地告诉你： 「通常为 245℃，具体以工艺文件为准。」

这个回答看起来对，但你没法用。因为它没说这个数字是从哪来的， 你也无法确认它是不是编的。

这就是我要解决的问题。听起来简单，做起来才发现 —— 这件事有三种完全不同的解法，而它们各自的代价差得很远。

一、问题比想象中麻烦

真正动手之后，我发现制造业工艺文档有三个特征，会让通用方案统统失效。

第一，表格太多。工艺参数、BOM 清单、检验规范，关键信息大量以表格形式存在。 你用常规手段把 PDF 转成文本，出来的是「层级 物料编码 物料名称 规格型号 用量 单位 物料属性 CJ30150001 组合仪表总成 CJ-3015 标准型 1 PCS 成品……」—— 行列对应关系全丢了。一个数字脱离了它所在的列，就等于没有信息。

第二，术语太专业。「波峰焊」「锡炉温度」「三防漆」「AQL」「GB/T 2828.1」 这些词，通用分词器切得乱七八糟。而中文的 BM25 关键词检索恰恰极度依赖分词质量。

第三，回答必须可核验。这不是闲聊场景。工程师拿一个工艺参数去调设备， 参数错了是要出生产事故的。所以答案必须能回溯到「第几页、第几节」。

这三个特征叠加起来，指向一个很明确的结论： 随手搭个 RAG 是没用的，每个环节都得认真做。

二、第一条路：从零写一个

我决定第一遍先把所有环节都自己实现一遍。原因很简单 —— 如果连每个环节在做什么都不清楚，用平台也只是在碰运气。

最终写了 11 个模块，全链路零外部服务依赖：

PDF/Word/MD 输入
  → 解析层：章节 / 表格 / 页码提取
  → 分词层：汽车电子领域词典 + bigram
  → 分块层：hybrid 策略（章节感知 + 滑动窗口）
  → 向量化：Qwen3-Embedding-4B，2560 维度
  → 索引层：本地 numpy 向量库 + BM25 倒排
  → 检索层：向量召回 + BM25 召回，RRF 融合
  → 重排层：关键词命中二次排序
  → 生成层：提示词约束 + 关闭思考模式
  → 输出：带原文引用的答案

有几个设计决定值得单独说。

为什么用 numpy 自己写向量库

不是因为造轮子有成就感，而是因为我想要的是一套能完全离线、零依赖启动的东西。 104 个片段的规模下，numpy 暴力检索耗时不到 0.3 秒，完全够用。

当然我也清楚这是权宜之计。所以索引接口是抽象过的 —— 规模上来了换成 FAISS 或 Milvus， 改动量很小。

溯源信息做到三级

很多 RAG 实现只保留「来自哪个文档」。我保留了三级： 章节 → 页码 → 片段类型。

片段类型这一级是刻意加的。因为工程师看到「第 12 页」还不够， 他需要知道「这是表格里的第 12 页」，才能判断这个数值的性质。

混合检索：为什么向量和 BM25 都要

单独用哪一个都有短板。向量检索擅长语义泛化，但对「GB/T 2828.1」这种精确编号容易漏； BM25 反过来，关键词一打一个准，但换个说法就找不到。

两路并行之后，用 RRF（倒数排名融合，k=60）合并。选 RRF 而不是加权求和，是因为 两路的分数尺度根本不可比 —— 余弦相似度在 0.6~0.9 之间， BM25 分数可以是任意正数，硬加权等于在瞎调参。

三、三个把我卡住的坑

坑一：向量模型选错了，命中率差 40 个百分点

一开始我用的是英文向量模型。想当然地觉得「向量表示嘛，跨语言应该能用」。

实测打脸：中文工艺查询的 Top1 命中率只有 60%。更诡异的是， 我打印了相似度分布，发现所有分数都挤在 0.67–0.68 这个极窄区间里。

这个现象在向量检索里叫语义空间坍缩 —— 模型没法区分这些中文文本， 输出的向量几乎指向同一个方向。它不是「排错了」，是「根本没能力排序」。

换成中文原生的 Qwen3-Embedding-4B 之后：

模型Top1 命中MRR维度
Nomic-Embed-Text-v1.5（英文）60%0.717768
Qwen3-Embedding-4B（中文）100%1.0002560

教训：中文领域做 RAG，向量模型必须用中文原生的。这不是「优化项」，是「及格线」。

坑二：模型输出为空，但 token 消耗拉满

这个坑最反直觉。

现象是：调接口，响应里 completion_tokens 显示 1024 以上，但 answer 字段是空的。而且单题耗时 27 到 175 秒不等。

我一度以为是接口协议不兼容，换了三种方式调都一样。

最后定位到：模型默认开启了思考模式。它会先生成一大段推理过程 （「让我分析一下用户的问题……资料里提到了……」），这段内容把输出配额占满了， 轮到真正的答案时已经没有 token 了。 而 OpenAI 兼容接口只读取正文内容字段，思考内容就落空了。

解法是在请求组装层强制注入关闭思考的参数。效果立竿见影：

同一道题：27–175 秒 / 输出为空 → 3.8–9.1 秒 / 答案完整准确。

顺带一提，我试过的无效方案有四种：enable_thinking: false、 chat_template_kwargs 注入、提示词追加控制标记、 thinking: {type: "disabled"} —— 全都没用。 只有那一个参数有效。

坑三：表格文字「脏」了正文，导致编号整体错位

这个问题非常隐蔽，表现是：表格编号整体错了一位。

排查后发现，PDF 里的表格内容会同时出现在两个地方 —— 正文文字流里有一份， 表格对象里也有一份。我的解析器把两份都收了，于是同一个表被数了两次，后面的编号就全部顺移。

修法不复杂：按真实的表标题来归并表格行，同时从正文流里剔除已经被表格捕获的文字。

效果：索引片段从 128 个收敛到 104 个，溯源位置恢复准确。

这类 bug 最麻烦的地方在于它不报错。系统照常运行，只是答案里的页码全差一页。 如果不是逐条核对溯源信息，根本发现不了。

四、第二条路：把活交给平台

自研链路跑通之后，我做了第二遍 —— 这次用 Dify。

动机很实际：自研链路证明了「我懂原理」，但它不证明「我会用工具」。 而真实工作里，能用成熟平台快速交付，往往比自己写更值钱。

Dify 1.17.1 全套 15 个容器跑起来，接上本机的 Qwen 模型。架构上的关键点是：

Dify 跑在容器里  ──host.docker.internal──▶  LM Studio 跑在宿主机

容器里的应用通过 host.docker.internal 反向调用宿主机的模型服务。 这个思路在工程上等价于生产环境的模型服务与应用解耦 —— 模型独立部署、独立扩缩容，应用只管编排。

实测 7 道题：

  • 6 道事实题全部正确，答案数值与源文档完全一致，且每题自动标注了依据（如「依据：CJ/WI-SMT-205」）
  • 1 道文档里根本没有的题，模型明确回答「知识库中未找到相关内容」
  • 平均延迟 6.40 秒

这个链路里踩的坑也很典型：镜像拉不下来、插件市场被网络拦截需要手动离线打包、离线包签名校验、 以及前面说的思考模式问题。其中「离线打包时 ZIP 里不能带目录条目」这个坑，我花了最久 —— 报错信息是 read _assets: is a directory，乍看完全不知道在说什么。

五、第三条路：让机器真正「看懂」文档

前两条路的解析环节，本质上都是先转文本、再处理。 而工艺文档最大的价值在表格里 —— 这正是纯文本路线最弱的地方。

所以我做了第三遍，用 RAGFlow 的 DeepDoc。

它的思路和前面完全不同：不上来就抽文字，而是先用视觉模型理解版面。

版面分析（layout.onnx）  →  判断这块区域是正文、标题、还是表格
文字识别（rec.onnx）     →  提取文字
表格结构识别（tsr.onnx） →  还原表格的行列结构
段落合并（XGBoost）      →  把碎块拼回完整段落

跑出来的结果确实不一样。它输出的不是纯文本，是结构化的 HTML 表格：

<table><caption>CJ-3015 组合仪表总成物料清单（BOM）</caption>
<tr><td>文件编号</td><td>CJ/BOM-3015</td></tr>
<tr><td>版本</td><td>D/1</td></tr>
<tr><td>生效日期</td><td>2026-04-15</td></tr>
</table>

注意那个 <caption> —— 表标题被单独识别出来了， 没有混进正文里。这一点很关键，因为「这张表叫什么」本身就是重要的检索线索。

更让我意外的是，每个片段还附带一张版面截图的标识。 也就是说，检索命中之后，你可以直接看到那片内容在原始 PDF 上的视觉位置， 而不只是一段文字。

5 份工艺文档全部解析成功，共切出 39 个片段。

当然，代价也很明显：慢。5 份文档总耗时 255 秒，平均每份 51 秒。 而且我用的社区镜像实际是 amd64 构建，在 M1 上要靠指令集转译运行 —— 这是额外的性能损失。

六、三选一？不，是三选三

做完三遍之后，我最想说的其实不是「哪个更好」，而是它们就不是一回事。

方案优势代价什么时候用
自研 RAG 轻量、可解释、零外部依赖、想改哪改哪 全部模块自己维护 资源受限、需深度定制、要求离线
Dify 快速交付、可视化编排、生态成熟 依赖平台、定制有天花板 标准化业务、快速验证
RAGFlow DeepDoc 唯一能同时还原表格结构和版面位置 慢、资源占用高 表格密集、对保真度要求高

如果只做一遍，我大概会得出「某某方案最好」的结论。做三遍之后才明白： 选型的本质是选代价。

你是更缺时间，还是更缺机器资源？你的文档里表格占多大比重？你的答案需不需要精确到 「第几页的哪张表」？—— 这些问题答完了，方案自然就出来了。

Dify 链路（7 题实测）：事实题 6/6 正确，拒答 1/1 正确，平均延迟 6.40 秒。

RAGFlow 链路：5 份文档解析全部成功，39 个片段。

特别想强调幻觉率 0% 这个数字。它不是靠模型能力堆出来的，是靠两道防线：

  1. 检索侧 —— 混合检索加重排，确保送进模型的资料真的相关；
  2. 生成侧 —— 系统提示硬性约束「只依据参考资料、缺失必须拒答、数值必须带单位和公差、句末方括号标注出处」。

评估集里我专门设计了 5 道文档里根本没有答案的题 （比如「变速箱齿轮的模数是多少」，而我们根本没有变速箱文档）。 模型 5 道全部主动拒答，没有一道编造。

这 5 道题才是这个项目里我觉得最重要的设计。因为 一个知识库系统的可信度，不取决于它能答对多少，而取决于它答不出来时会不会硬编。

八、我学到了什么

第一，先做一遍再谈选型。我如果一开始就挑了某个平台直接用， 大概率会卡在某个环节然后归因错误 —— 比如把「向量模型选错」误判成「平台不行」。 自己做一遍，才知道每个环节的正常表现该是什么样。

第二，报错信息经常指错方向。「输出为空但 token 拉满」看起来像协议问题， 实际是模型行为问题；「表格编号错位一位」看起来像分页 bug，实际是数据重复。 要顺着现象往下挖到机制层，而不是停在报错文字上。

第三，能测的都要测。幻觉率 0% 这个数字，是靠 25 道题、5 道反例、 逐条核对关键词覆盖换来的。如果只是「跑通了几道题感觉还行」， 这个项目在面试里一句话就会被问穿。

第四，诚实地标注边界。这个项目里有几件事我明确没做：RAGFlow 的检索问答链路没配、 文档数据是按行业规范构造的仿真数据、向量库是自研的 numpy 实现而不是生产级方案。 把这些写清楚，比把它们藏起来更有价值 —— 因为面试官迟早会问到，而主动说出来，反而说明你知道边界在哪。
